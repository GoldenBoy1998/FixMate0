# ربط FixMate مع Lovable.dev وGitHub

## النتيجة المهمة

تحققنا من توثيق Lovable الرسمي: Git Sync في Lovable يعمل بطبقتين، اتصال مساحة العمل بحساب GitHub ثم ربط مشروع Lovable بمستودع واحد. عند ربط مشروع Lovable لأول مرة، ينشئ Lovable مستودعًا جديدًا ويبدأ المزامنة ثنائية الاتجاه. لا يوفّر Git Sync طريقة لربط مشروع Lovable بمستودع GitHub موجود مسبقًا كما هو.

المراجع الرسمية:

- [توثيق Lovable عن GitHub Sync](https://docs.lovable.dev/integrations/github)
- [نظرة عامة على Git Sync](https://docs.lovable.dev/integrations/git-sync-overview)
- [الأسئلة الشائعة عن استيراد مشروع موجود](https://docs.lovable.dev/introduction/faq)

## ماذا يعني ذلك لمستودع FixMate؟

مستودع FixMate الحالي هو:

```text
https://github.com/GoldenBoy1998/FixMate0
```

والفرع الذي يحتوي آخر تطوير هو:

```text
autonomous/production-foundation
```

لا يمكن من داخل ملفات FixMate منح Lovable صلاحية GitHub أو إنشاء OAuth installation؛ هذه صلاحية خارجية يجب أن يمنحها صاحب حساب GitHub من واجهة GitHub/Lovable. كما أن منح صلاحية Lovable للمستودع لا يتم بتعديل `package.json` أو ملف إعداد داخل المشروع.

## المسار الآمن الموصى به

### المسار الأول: استخدام FixMate كمصدر استيراد إلى Lovable

1. نزّل ملف `FixMate-Lovable-import.zip` المرفق مع هذه المرحلة.
2. افتح Lovable وأنشئ مشروعًا أو استخدم مشروعًا مستوردًا.
3. اختر استيراد مشروع موجود وارفع ملف ZIP.
4. راجع الملفات والتغييرات التي سيعيد Lovable بناءها قبل قبولها.
5. من **Project settings → Git** أضف اتصال GitHub.
6. عند فتح GitHub، اختر حسابك أو المنظمة المناسبة.
7. اختر **Only select repositories** بدل **All repositories** كلما أمكن.
8. إذا أنشأ Lovable مستودعًا جديدًا، لا تحذف مستودع FixMate الأصلي. اعتبر المستودع الجديد نسخة منفصلة إلى أن تتم مراجعة الفروقات.

حسب توثيق Lovable، استيراد ZIP قد يعيد بناء التطبيق ونقل قاعدة البيانات والمستخدمين إلى backend الخاص بـ Lovable. لذلك لا ينبغي اعتبار الاستيراد ترقية شفافة لخادم Express/PostgreSQL الحالي. يجب مراجعة البنية الناتجة قبل استخدامه كمصدر إنتاج.

### المسار الثاني: إبقاء FixMate على GitHub الحالي

إذا كان الهدف هو استمرار FixMate على Express وPostgreSQL وDrizzle كما هو، فالمسار الأكثر أمانًا هو إبقاء مستودع `GoldenBoy1998/FixMate0` هو المصدر الأساسي، واستخدام Lovable فقط كمساعد أو كمشروع منفصل. لا تربط مستودعًا جديدًا ناتجًا من Lovable بالمشروع الأصلي تلقائيًا، لأن ذلك قد يسبب اختلافًا في البنية أو الكتابة فوق التغييرات.

يمكن نقل التغييرات بين المستودعين عبر Pull Request ومراجعة يدوية، وليس عبر مزامنة عمياء.

## الصلاحيات المطلوبة

عند تثبيت تطبيق Lovable من GitHub، يتيح GitHub اختيار:

- كل المستودعات.
- مستودعات محددة فقط.

الأفضل لمشروع FixMate هو اختيار مستودع محدد. يجب أن تكون مالكًا أو مشرفًا على حساب GitHub أو المنظمة حتى تتمكن من تثبيت التطبيق وربط مساحة العمل. وفي Lovable، إنشاء أو تعديل اتصال مساحة العمل يحتاج عادةً إلى صلاحية مالك أو مشرف مساحة العمل، بينما ربط المشروع بالمستودع يحتاج صلاحية مالك أو مشرف المشروع.

## قيود مهمة قبل التفعيل

- كل مشروع Lovable يرتبط بمستودع واحد وفرع متزامن واحد في الوقت نفسه.
- التغييرات في الفروع الأخرى لا تظهر في Lovable حتى يتم تبديل الفرع المتزامن أو دمج التغييرات.
- إذا حدث تباعد بين Lovable وGitHub، قد يستخدم Lovable فرعًا باسم `lovable-sync` بدل الكتابة المباشرة على الفرع المتزامن.
- حذف المستودع المتصل يوقف المزامنة.
- Push إلى GitHub لا يعني نشر الموقع مباشرةً؛ المزامنة شيء والنشر شيء آخر.
- Lovable ليس مزود تسجيل دخول لمستخدمي FixMate؛ هو منصة تطوير ومزامنة كود.

## ما لا ينبغي فعله

لا تمنح Lovable صلاحية **All repositories** إذا كان المطلوب هو FixMate فقط. لا تضع مفاتيح PostgreSQL أو كلمات مرور الإدارة في ZIP أو GitHub. لا تستبدل `main` أو الفرع الإنتاجي بتغييرات Lovable قبل مراجعة Pull Request. لا تفترض أن backend الخاص بـ Lovable يحافظ تلقائيًا على Express/PostgreSQL الحالي.

## قرار المشروع الحالي

لم يتم منح Lovable صلاحية GitHub تلقائيًا، لأن ذلك يتطلب تفاعلًا خارجيًا من حساب المالك، ولأن Git Sync لا يربط مستودع FixMate الحالي مباشرةً حسب توثيق Lovable. تم تجهيز نسخة ZIP نظيفة من commit الحالي لتكون خيار الاستيراد الرسمي، مع إبقاء مستودع FixMate الأصلي وفرع التطوير دون تغيير.
