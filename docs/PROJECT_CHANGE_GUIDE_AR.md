# دليل تغييرات مشروع FixMate من البداية إلى الآن

## 1. الغرض من هذا الملف

هذا الدليل يشرح الحالة الفعلية لمشروع FixMate منذ نقطة البداية في مستودع GitHub وحتى آخر تغيير موجود على الفرع `autonomous/production-foundation`. الهدف هو أن يفهم المطور أو صاحب المشروع:

- ماذا كان المشروع في البداية؟
- ما الذي تغيّر في قاعدة البيانات والخادم والواجهة؟
- ما وظيفة كل ملف تم إنشاؤه أو تعديله؟
- كيف يتم تعديل الملفات بأمان؟
- ما الملفات التي لا يجب تعديلها مباشرةً، وما الذي يحتاج إلى PostgreSQL أو إعدادات خارجية؟
- ما الذي تم التحقق منه، وما الذي ما زال يحتاج إلى تحقق فعلي؟

هذا المستند يصف التنفيذ الموجود في Git، وليس خطة نظرية منفصلة.

---

## 2. نقطة البداية: حالة المشروع قبل التطوير

كان FixMate تطبيق React/Vite تجريبيًا لخدمات الصيانة في السودان. كانت الواجهة عربية وباتجاه RTL، وتحتوي على الصفحة الرئيسية، فئات الخدمات الثماني، نموذج طلب صيانة، تسجيل فني، لوحة عميل، لوحة فني، ولوحة إدارة.

لكن البيانات التشغيلية كانت محفوظة في `localStorage` تحت مفتاح تجريبي. لذلك كان اختيار الدور في شاشة الدخول محاكاة فقط، ولم يكن هناك حساب حقيقي أو جلسة أو صلاحيات حقيقية أو قاعدة بيانات مركزية. كان خادم Express يوفّر تقريبًا فحص صحة فقط، بينما لم يكن مخطط PostgreSQL قد أصبح مصدر الحقيقة للطلبات والمستخدمين.

المشكلات الأساسية في تلك المرحلة كانت:

1. يمكن لأي مستخدم متصفح تقليد دور الإدارة أو الفني.
2. الطلبات لا تنتقل بين الأجهزة ولا تُحفظ مركزيًا.
3. لا توجد مصادقة حقيقية أو تشفير كلمات مرور.
4. لا توجد حماية backend للطلبات أو انتقالات الحالة.
5. لا توجد إشعارات أو سجل تدقيق أو مرفقات محمية.
6. لا توجد دورة اختبار كاملة من التسجيل حتى إكمال الطلب.

## 3. ما الذي حدث في مراحل التنفيذ؟

### المرحلة الأولى: التدقيق والعزل

تم فحص مستودع `GoldenBoy1998/FixMate0`، ثم تم العمل على فرع مستقل اسمه:

```text
autonomous/production-foundation
```

الهدف من ذلك هو إبقاء `main` دون دمج حتى تكتمل المراجعة والاختبارات المطلوبة. تم الاحتفاظ بمرجع نقطة البداية في commit `1841ba6` الموجود على `main`.

### المرحلة الثانية: تأسيس backend وقاعدة البيانات

تم تصميم نموذج PostgreSQL باستخدام Drizzle ORM. أصبح النظام يعرف الكيانات التالية:

- المستخدمون والجلسات.
- ملف العميل وملف الفني.
- فئات الخدمات.
- تخصصات الفنيين ومناطق خدمتهم.
- طلبات الصيانة.
- سجل انتقالات حالة الطلب.
- الملاحظات.
- المرفقات.
- الإشعارات.
- سجل التدقيق الإداري.

تم إنشاء migration أولي وseed للفئات الثماني وحساب الإدارة. كما أضيف تشفير كلمات المرور باستخدام `scrypt` وجلسات opaque عشوائية، بحيث لا تُحفظ قيمة الجلسة الخام داخل قاعدة البيانات؛ المخزن هو hash للجلسة فقط.

### المرحلة الثالثة: المصادقة والصلاحيات

تم تنفيذ:

- تسجيل العميل أو الفني.
- تسجيل الدخول بالبريد الإلكتروني أو الهاتف.
- تسجيل الخروج وحذف الجلسة.
- قراءة المستخدم الحالي عبر `/api/auth/me`.
- جلسات محفوظة في PostgreSQL ومُرسلة داخل HttpOnly cookie.
- منع إنشاء حساب إدارة من الواجهة العامة.
- جعل حساب الفني في حالة `pending` حتى يعتمد من الإدارة.
- middleware يتحقق من الجلسة والدور وحالة الحساب.

تمت إضافة حماية إعدادات cookies بحيث لا يمكن تشغيل `SameSite=None` دون `Secure=true`.

### المرحلة الرابعة: API ودورة الطلب

تم تنفيذ API للفئات والطلبات، مع دورة حالات يتحقق منها الخادم، وليس المتصفح فقط:

```text
submitted
under_review
assigned
accepted
in_progress
completed
closed
```

وتوجد حالات بديلة أو نهائية:

```text
rejected
cancelled
unable_to_complete
reassignment_required
```

تمت إضافة إنشاء الطلب للعميل، عرض الطلبات بحسب الدور، عرض سجل الحالة، إسناد الطلب إلى فني معتمد، قبول الطلب، بدء التنفيذ، الإكمال، والإلغاء المسموح.

### المرحلة الخامسة: ربط الواجهة

تم استبدال المتجر التجريبي في `App.tsx` بواجهة تستعمل API والمصادقة الحقيقية. أصبحت الصفحات الرئيسية، الخدمات، الدخول، التسجيل، طلب الصيانة، لوحات العميل والفني والإدارة تقرأ وتكتب عبر الخادم.

تم الإبقاء على `localStorage` لتفضيل اللغة فقط، وليس لبيانات الأعمال. كما تم إضافة تبديل شامل بين العربية والإنجليزية، مع تغيير:

```text
html.lang
html.dir
```

على مستوى الموقع كاملًا.

### المرحلة السادسة: الإدارة والإشعارات والمرفقات

تمت إضافة لوحة إدارة للفنيين والفئات والطلبات. يمكن للإدارة اعتماد الفني أو رفضه، تعطيل فئة، عرض الطلبات، وإسناد الطلب إلى فني معتمد.

تمت إضافة إشعارات داخلية مرتبطة بالمستخدم، مع حالة مقروء/غير مقروء. كما تمت إضافة رفع صورة أو PDF مع الطلب بحد أقصى 5 ميجابايت، وقائمة MIME محددة، ومفتاح تخزين عشوائي، وصلاحيات وصول مرتبطة بملكية الطلب أو إسناده.

التخزين الحالي للمرفقات محلي ومناسب للتطوير فقط، داخل:

```text
.data/uploads
```

هذا المجلد متجاهل في Git. قبل الإنتاج يجب استبداله بمخزن خاص دائم مع سياسة نسخ احتياطي وفحص ملفات مناسب.

## 6. كيف تعدّل المشروع بالطريقة الصحيحة؟

### عند إضافة حقل جديد إلى قاعدة البيانات

الترتيب الصحيح هو:

1. عدّل `lib/db/src/schema/index.ts`.
2. ولّد migration جديدة باستخدام أمر Drizzle الموجود في `lib/db/package.json`.
3. راجع SQL الناتج.
4. حدّث seed إن كان الحقل يحتاج قيمة ابتدائية.
5. حدّث route validation في الخادم.
6. حدّث نوع API والواجهة.
7. شغّل typecheck وbuild.
8. اختبر migration على قاعدة فارغة وعلى قاعدة تحتوي بيانات.

لا تبدأ بتعديل ملف SQL الناتج ثم تحاول عكس التغيير في schema؛ هذا يسبب اختلافًا بين المصدر والقاعدة.

### عند إضافة endpoint جديد

1. أنشئ أو عدّل route داخل `artifacts/api-server/src/routes`.
2. استخدم `zod` للتحقق من body والـ params.
3. استخدم `requireAuth` و`requireRole` عند الحاجة.
4. افحص ملكية المورد داخل الخادم.
5. أضف route إلى `routes/index.ts` إذا كان router جديدًا.
6. أضف الدالة والنوع إلى `artifacts/fixmate/src/lib/api.ts`.
7. اربط الواجهة بالدالة المركزية.
8. حدّث `docs/API.md` و`lib/api-spec/openapi.yaml`.
9. أضف اختبارًا للحالة المسموحة والمرفوضة.

### عند تعديل دورة حالة الطلب

يجب تعديل كل هذه المواضع معًا:

- `requestStatusEnum` في schema.
- `statusSchema` في `requests.ts`.
- جدول `allowed` وانتقالات الصلاحيات في `requests.ts`.
- النصوص والأزرار في الواجهة.
- OpenAPI.
- اختبارات workflow.
- الإشعارات الناتجة عن الانتقال.

لا يكفي إضافة زر جديد في React؛ الخادم هو السلطة النهائية.

### عند تعديل المصادقة

- لا تخزن raw password.
- لا تخزن raw session token في PostgreSQL.
- لا تنقل session token إلى JavaScript أو localStorage.
- أي `SameSite=None` يحتاج `Secure=true` وHTTPS.
- يجب اختبار تسجيل الدخول، انتهاء الجلسة، logout، والوصول بحساب غير مصرح.
- يجب أن يبقى دور admin غير قابل للإنشاء من التسجيل العام.

### عند تعديل المرفقات

- استخدم MIME allowlist لا امتداد اسم الملف فقط.
- حافظ على حد الحجم.
- ولّد storage key عشوائيًا ولا تستخدم اسم المستخدم كما هو في المسار.
- افحص ملكية الطلب قبل upload وقبل download.
- لا تجعل مجلد الملفات العامة قابلًا للتصفح المباشر.
- في الإنتاج استخدم private object storage مع URLs مؤقتة أو proxy محمي.

### عند تعديل اللغة

اللغة تفضيل واجهة عالمي، وليست خاصية للصفحة الرئيسية فقط. عند إضافة نص جديد:

1. أضف النسخة العربية والإنجليزية.
2. لا تستخدم نصًا عربيًا ثابتًا داخل مسار الإنجليزية إذا كان النص جزءًا أساسيًا من الشاشة.
3. اختبر `document.documentElement.lang` و`document.documentElement.dir`.
4. راجع اتجاه الأيقونات والأسهم وحقول الهاتف والبريد التي قد تحتاج `dir="ltr"`.

## 7. ما الذي لا ينبغي تعديله مباشرةً؟

عبارة «لا يمكن تعديله» تعني هنا: لا تعدّله يدويًا لأنه ملف مولد أو لأنه يحتاج قرارًا خارجيًا، وليس أن نظام الملفات يمنع التعديل تقنيًا.

### ملفات مولدة أو مرتبطة بأداة

لا تعدّل يدويًا:

- `pnpm-lock.yaml`: استخدم pnpm.
- `lib/db/drizzle/*.sql`: عدّل schema ثم ولّد migration.
- `lib/db/drizzle/meta/*`: تديرها Drizzle.
- `artifacts/*/dist`: ناتج build، ويجب ألا يكون مصدرًا للتعديل.
- أي generated API client إن تمت إعادة توليده من OpenAPI.

### ملفات لا يجوز أن تحتوي أسرارًا

لا تضع كلمات مرور أو مفاتيح API أو DSN حقيقيًا داخل:

- `.env.example`.
- README أو docs.
- React source.
- OpenAPI.
- Git history.

القيم الحقيقية يجب أن تكون في `.env` محليًا أو مدير أسرار في بيئة النشر.

### أشياء لا يمكن حسمها بالشفرة وحدها

تحتاج هذه البنود إلى بيئة أو قرار خارجي:

1. تشغيل migration وseed فعليًا يحتاج PostgreSQL و`DATABASE_URL`.
2. اختبار دورة المستخدمين الحقيقي يحتاج بيانات قاعدة ويفضل بيئة اختبار منفصلة.
3. التخزين الدائم للمرفقات يحتاج object storage أو volume دائم وقرارًا تشغيليًا.
4. النشر يحتاج domain وHTTPS وإعداد reverse proxy أو منصة نشر.
5. rate limiting وCSRF يعتمد جزء منه على topology النهائي للواجهة والخادم.
6. النسخ الاحتياطي والاستعادة يتطلبان سياسة تشغيلية واختبار restore فعليًا.
7. المراجعة الأمنية والاختبار الاختراقي يحتاجان مختصًا أو بيئة مخصصة.
8. تغيير الترخيص أو أسماء التواصل الرسمية يحتاج قرار مالك المشروع.

### main والدمج

لا ينبغي دفع هذه التغييرات إلى `main` أو دمجها قبل إغلاق بوابات الإطلاق. الفرع الحالي مقصود أن يبقى معزولًا إلى أن تتوفر PostgreSQL واختبارات دورة كاملة ومراجعة أمنية.

## 8. الحالة الحالية: مكتمل، جزئي، متبقٍ

### مكتمل ومتحقق بنيويًا

- مخطط PostgreSQL وmigration الأولي.
- seed للفئات الثماني وحساب الإدارة.
- scrypt password hashing.
- opaque sessions وHttpOnly cookie.
- تسجيل العميل والفني وتسجيل الدخول والخروج والمستخدم الحالي.
- middleware للأدوار والملكية.
- API للفئات والطلبات والإسناد وانتقالات الحالة.
- إدارة الفنيين والفئات والطلبات.
- الإشعارات الداخلية وحالة القراءة.
- رفع مرفق محدود النوع والحجم مع فحص الصلاحيات.
- دعم العربية والإنجليزية وتبديل RTL/LTR.
- بناء frontend وbackend وtypecheck.
- فحص `/api/healthz` محليًا.
- رفض إعداد cookie غير الآمن.

### منفذ لكنه غير متحقق بالكامل

- دورة التسجيل إلى إكمال الطلب لم تُنفذ على PostgreSQL حقيقية في هذه البيئة.
- الرفع الحالي محلي وليس object storage إنتاجيًا.
- لم يتم اختبار كل تفاعلات المتصفح بصريًا.
- لم تتم تغطية كل الفروع باختبارات آلية.

### ما يجب إنجازه قبل الإطلاق

- إضافة اختبارات frontend وbackend وintegration وworkflow.
- تنفيذ migration وseed على PostgreSQL نظيفة.
- تشغيل دورة كاملة: عميل، فني، اعتماد، إسناد، قبول، تنفيذ، إكمال.
- إضافة rate limiting للمصادقة.
- إضافة CSRF strategy مناسبة لطريقة النشر.
- إضافة secure private storage وفحص ملفات متقدم.
- تنفيذ backup/restore drill.
- مراجعة أمنية نهائية.
- تحديث `docs/INSTALLATION.md` ليعكس أن الواجهة أصبحت مرتبطة فعليًا بدل الوصف القديم.

## 11. قاعدة مختصرة للمطور القادم

إذا كان التغيير متعلقًا بالبيانات، ابدأ من schema. إذا كان متعلقًا بالصلاحيات، طبقه في الخادم قبل الواجهة. إذا كان متعلقًا بالواجهة، مرر البيانات عبر `api.ts` ولا تستخدم localStorage للبيانات التشغيلية. إذا كان متعلقًا بملف مولد، استخدم الأداة التي تولده. وبعد كل تغيير شغّل typecheck وbuild وحدّث التوثيق والاختبارات المناسبة.
